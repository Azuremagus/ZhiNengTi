# 软件工程 · 领域知识图谱

## 一、知识地图

```
软件工程
├── 开发过程
│   ├── 过程模型：瀑布 → 迭代 → 敏捷（Scrum/XP）→ DevOps
│   ├── 需求工程：需求获取、建模、追踪性
│   └── 软件设计：架构风格、设计模式、API 设计
├── 质量保障
│   ├── 软件测试：单元/集成/系统测试、覆盖率、模糊测试、变异测试
│   ├── 静态分析：数据流分析、符号执行、类型系统
│   ├── 形式化方法：模型检测、定理证明
│   └── 代码评审：现代评审流程、评审者推荐
├── 维护演化
│   ├── 缺陷定位与自动修复（APR）
│   ├── 重构与技术债
│   ├── 软件仓库挖掘（MSR）：commit/issue/PR 数据分析
│   └── 版本兼容与依赖管理
├── 人机协作
│   ├── 开发者生产力度量
│   └── 开源社区与协作机制
└── AI 交叉（当前最活跃）
    ├── AI4SE：代码生成、代码摘要、缺陷预测、自动评审
    ├── SE4AI：ML 系统测试、模型运维（MLOps）、AI 工程质量
    └── LLM 编程助手的人机协同研究
```

## 二、核心概念速览

| 概念 | 一句话 | 常见研究点 |
|---|---|---|
| 技术债 | 为短期交付牺牲长期质量的隐性成本 | 量化、偿还优先级 |
| 代码异味 | 暗示设计问题的表面症状 | 自动检测、与缺陷的关联 |
| 覆盖率 | 测试执行的代码比例 | 行/分支/路径覆盖的局限 |
| 模糊测试 | 随机/变异输入找崩溃 | 覆盖率引导（AFL）、LLM 生成种子 |
| APR | 自动生成补丁修缺陷 | 基于模板/学习/LLM 三代方法 |
| 缺陷预测 | 预测哪些文件/变更易出错 | 特征工程 vs 深度学习 vs LLM |
| 实证研究 | 用数据回答 SE 问题 | MSR 数据、受控实验、案例研究 |
| 开发者生产力 | 交付效率与质量的综合 | SPACE 框架、度量的滥用风险 |

## 三、经典资源

### 教材与著作
- 《软件工程》(Ian Sommerville) — 通识教材
- 《代码大全》(Code Complete) — 构建实践
- 《重构》(Martin Fowler) — 重构目录
- 《人月神话》(Brooks) — 过程与人的经典论断

### 顶会（CCF-A 为主）
- ICSE、FSE（ESEC/FSE）、ASE — SE 三大顶会
- ISSTA — 测试与分析
- MSR — 软件仓库挖掘
- ICSME — 维护与演化

### 数据与工具
- GitHub / GH Archive：仓库挖掘数据源
- Defects4J（Java 缺陷基准）、ManySStuBs4J
- SWE-bench：LLM 修真实 GitHub issue 的基准（AI4SE 当前热点）
- CodeQL：语义代码分析引擎

## 四、常见研究问题

- **AI4SE 主线**：LLM 代码生成的正确性评估（HumanEval→SWE-bench 的演进）；代码大模型的幻觉与安全问题；仓库级（而非函数级）代码理解与生成
- **测试主线**：模糊测试的效率；LLM 生成测试用例；深度学习系统的测试（SE4AI）
- **实证主线**：开发者使用 AI 助手前后的生产力与代码质量变化；开源社区的可持续性
- **维护主线**：依赖供应链风险（如 npm/PyPI 生态）；技术债的量化管理

## 五、SE 研究方法提示

SE 是强实证学科，评审格外看重：
1. **研究问题的真实性**：来自真实开发场景的痛点，而非人造场景
2. **数据的说服力**：工业界数据 > 大规模开源数据 > 小规模玩具数据
3. **基线的现代性**：2024 年后的 SE 论文，代码类任务基线必须包含 LLM 方法
